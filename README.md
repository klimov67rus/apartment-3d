# ПЛАН / 3D

Локальный прототип универсального построения квартир из JSON. Python-производитель данных не зависит от Three.js. Viewer по умолчанию показывает автоматически созданное приблизительное превью plan.jpg. Для растровых изображений добавлен независимый первый этап: поиск кандидатов стен в пикселях с диагностическим наложением.

## Запуск

Версии инструментов и команды проекта задаются в `mise.toml`: Node.js 24, Python 3.12 и uv. mise устанавливает интерпретаторы; npm и uv устанавливают зависимости в `node_modules/` и `.venv/`. uv не скачивает собственный Python: при настройке используется интерпретатор mise.

Установите [mise по официальной инструкции](https://mise.jdx.dev/getting-started.html), затем из корня проекта:

```bash
mise trust
mise install
mise run setup
mise run dev
```

`mise run` не требует активации shell. Если mise установлен в `~/.local/bin`, добавьте этот каталог в PATH либо вызывайте `~/.local/bin/mise`. Для автоматического переключения инструментов в zsh можно добавить `eval "$(mise activate zsh)"` в свою конфигурацию shell.

Откройте http://127.0.0.1:5173. `mise run dev` запускает viewer и локальный Python-сервис распознавания на 127.0.0.1:8765; Vite при занятом порте выведет другой адрес. Для загрузки планов оба процесса должны работать. Остановка обоих — Ctrl+C.

```bash
mise run test
mise run build
mise run validate
```

Произвольную Python-команду выполняйте через `mise exec -- uv run python …`. Кэш uv хранится в `.cache/uv/` внутри проекта. Существующая `.venv`, созданная системным Python, при `setup` может быть пересоздана uv под Python mise; исходные файлы это не затрагивает.

`mise run build` выполняет TypeScript-проверку и создаёт `viewer/dist/`. Версии в `mise.toml` задают ветки обновлений; точные релизы инструментов записаны в `mise.lock`, зависимости — в `package-lock.json` и `uv.lock`. Все три lock-файла созданы. При намеренном обновлении инструментов обновляйте `mise.lock` командой `mise lock`. Для установки пакетов строго по lock-файлам используйте `mise exec -- npm ci` и `mise exec -- uv sync --locked --python "$(mise which python)"`.

## Что реализовано

- `schema/apartment.schema.json`: единый контракт, версия 1.0, стены, комнаты, дверные/оконные проёмы, экземпляры мебели и словарь GLB-моделей.
- `recognizer/cli.py`: команды `validate`, `calibrate`, `recognize`, независимые от viewer. Shapely проверяет полигоны помещений.
- `recognizer/walls.py`: OpenCV-поиск кандидатов стен и диагностическое наложение; `schema/wall-candidates.schema.json` задаёт отдельный промежуточный контракт без выдуманных комнат и высот.
- `viewer/src/model.ts`: проверка схемы и связей перед построением. Отклоняются нулевые стены, пересечения проёмов, неизвестные ссылки, выходы проёмов за границы стены и самопересечения помещений.
- `viewer/src/geometry.ts`: полы по полигонам, прямые стены произвольного направления, геометрические проёмы. Прямоугольные части стены строятся между границами проёмов; поддерживаются несколько окон по высоте.
- `viewer/src/main.ts`: обзор с OrbitControls, план сверху, свободная прогулка с PointerLockControls, редактирование/импорт/экспорт JSON. Ошибочные данные не заменяют последнюю рабочую сцену. Изменения сохраняются только экспортом JSON.
- `viewer/public/examples/apartment.json`: синтетическая квартира 8 × 6 м, три помещения, три двери, два окна. Размеры заданы явно, это не результат измерения изображения.

## Автоматический MVP

Ручное подтверждение больше не является этапом обработки. Команда запускает распознавание стен, нормализацию, поиск проёмов и оценку полов подряд:

```bash
mise exec -- uv run python -m recognizer.cli generate plan.jpg --output artifacts/my-auto-run
```

Команда создаёт новый каталог и не перезаписывает существующие данные. `walls-pixels.json` и `openings-pixels.json` сохраняют координаты в пикселях и неизвестный масштаб. `apartment-preview.json` — автоматически сформированное приближённое превью с `scale.status: estimated`, масштабом, оценённым по двери шириной 0,8 м, высотой стены 2,7 м и условными высотами проёмов. Оно совместимо с viewer через «Открыть JSON». Пиксельный результат не выдаётся за метрическую калибровку.

Для демонстрационного плана viewer по умолчанию загружает автоматический результат `viewer/public/examples/plan-automatic.json`, созданный из [результата обработки](artifacts/window-final/plan/apartment-preview.json), без использования `review.json`. Для другого изображения нажмите «Загрузить план JPG / PNG»: viewer отправит файл локальному Python-сервису, автоматически построит сцену и совместит исходное изображение с геометрией. JSON можно сохранить кнопкой «Сохранить JSON».

Типы, обнаруженные алгоритмом, применяются автоматически. Неопределённые проёмы остаются разрывами; при незамкнутых стенах пол оценивается по выпуклой оболочке с предупреждением. На тестовом изображении эвристика ошибочно классифицирует один проём и пропускает крупное окно. Автоматический результат требует дальнейшего улучшения качества на размеченном наборе планов; ручная проверка не блокирует конвейер. Старые файлы `review.json` и вручную подготовленное превью сохранены как история эксперимента, в MVP не используются.

## Загрузка изображения в viewer

Выберите «Загрузить план JPG / PNG». Файл обрабатывается локальным Python-сервисом, после чего viewer показывает результат и исходное изображение как подложку. Распознавание выполняется автоматически, без ручного подтверждения. Если файл повреждён, формат не поддерживается или по дверям нельзя оценить масштаб, появится сообщение, а предыдущая сцена сохранится.

Поддерживаются JPG и PNG до 15 МиБ; обработка изображений ограничена 24 млн пикселей. Передача и обработка происходят на локальном компьютере; временные файлы удаляются после ответа. Чтобы сохранить сгенерированную квартиру, используйте «Сохранить JSON». При повторном открытии JSON исходное изображение не сохраняется внутри него, поэтому подложка автоматически не восстанавливается. Сборка `mise run build` создаёт статический frontend; для интерактивного распознавания запускайте `mise run dev`, который поднимает и Python-сервис.

Проверено в Chromium: загрузка `1-floor.jpg`, автоматическая сцена, совмещение подложки, её переключение и сохранение предыдущей сцены после повреждённого файла. [Снимок проверки](docs/verification/upload-preview.png). HTTP-тесты проверяют реальный план, тип файла, размер и ограничение источника запроса.

## Оценка масштаба по дверям

При `generate` измеряются пиксельные ширины распознанных дверей; для них предполагается ширина 0,8 м. Берётся медиана, отбрасываются значения, отличающиеся от неё более чем на 25%, затем вычисляется масштаб по медиане оставшихся. Требуются минимум две согласующиеся двери с отношением максимальной ширины к минимальной не более 1,5. Данные оценки и отброшенные значения сохраняются в `scale.json`. Это эвристика: две ошибки распознавания могут совпасть, а реальная ширина дверей может отличаться от 0,8 м.

Если согласующихся дверей недостаточно, сохраняются только пиксельные стены и проёмы и `scale.json` со статусом `unknown`; метрическое превью не создаётся. При успехе статус — `estimated`, реальные размеры и площади остаются приблизительными. Подложка демонстрационного `plan.jpg` использует тот же оценочный масштаб.

Прогон четырёх квартир из `examples/floor-plans`: `1-floor-2` — 0,004706 м/px; `1-floor` — 0,004938 м/px; `2-floor-1` — 0,004706 м/px; `3-floor-1` — 0,005263 м/px. Результаты в `artifacts/door-scale/`. Кладовка исключена из набора MVP и прогона. Это не проверка физической точности: контрольных размеров нет. Проверены выброс, недостаток дверей, пересчёт при изменении разрешения, создание превью и защита исходника.

## Эксперимент с белыми полями

Проверен вариант расчёта порогов стен по габаритам тёмного содержимого вместо размера изображения. На четырёх новых примерах количество областей пола изменилось: 2→3, 1→3, 2→6 и 4→5. Одновременно на исходном `plan.jpg` кандидатов стен стало 61 вместо 33, а областей пола — 9 вместо 6. Без эталонной разметки рост количества не означает улучшение; вероятны ложные стены и разделения. Вариант отклонён и не включён в основной алгоритм. Экспериментальные файлы сохранены в `artifacts/content-bounds/` и `artifacts/plan-content-bounds/`.

Текущий алгоритм всё ещё зависит от белых полей, а далёкие подписи также мешают надёжно определить границы самого чертежа. Вариант дополнительно сравнен с размеченными планами: на исходном плане доля подходящих стен по длине уменьшилась с 95% до 76%, а число лишних областей пола выросло с 1 до 2. Проверка регрессий отклоняет этот вариант.

## Эталон и регрессионные проверки

В `tests/fixtures/floorplan-benchmark/` подготовлена приблизительная полная разметка видимых стен, окон и помещений для `plan.jpg`, `1-floor.jpg` и `2-floor-1.jpg`. Она нанесена вручную по растру и предназначена только для тестирования; новые планы обрабатываются без ручного этапа. Границы обозначений, особенно у лоджий и толстых стен, могут трактоваться по-разному, поэтому показатели зависят от этого эталона и не являются строительными измерениями.

Проверочные изображения: [исходный план](tests/fixtures/floorplan-benchmark/plan-annotation.jpg), [однокомнатная квартира](tests/fixtures/floorplan-benchmark/1-floor-annotation.jpg), [двухкомнатная квартира](tests/fixtures/floorplan-benchmark/2-floor-1-annotation.jpg). Синий — стены, оранжевый — окна, зелёный — контуры пола. Файлы JSON содержат размеры и SHA-256 исходного изображения, чтобы случайно не сравнивать результат с другим планом.

```bash
mise run benchmark
mise exec -- uv run python -m recognizer.benchmark \
  tests/fixtures/floorplan-benchmark/1-floor.json artifacts/window-final/1-floor
```

Сравнение оценивает длину линий стен в пределах 20 px от эталона (доля найденной длины и покрытие эталона); окна сопоставляются взаимно однозначно по направлению и перекрытию с допуском 25 px и порогом 50%; помещения — взаимно однозначно при IoU ≥ 0,5. Для окон и помещений выводятся совпадения, лишние и пропущенные объекты. Эти допуски заданы в пикселях конкретных эталонов, поэтому не гарантируют одинаковое качество на других разрешениях. Двери и точность масштаба этим набором количественно не оцениваются.

| План | Окна: до → сейчас (найдено / лишних / пропущено) | Помещения: до → сейчас |
| --- | --- | --- |
| `plan.jpg` | 0/1/3 → 1/1/2 | 5/1/2 → 5/1/2 |
| `1-floor.jpg` | 0/0/2 → 1/0/1 | 1/0/4 → 2/0/3 |
| `2-floor-1.jpg` | 0/0/3 → 1/0/2 | 2/0/5 → 3/0/4 |

Исходные и текущие показатели сохранены в `*-baseline.json` и `*-current.json`, а результаты последнего прогона — в `artifacts/window-final/`. `mise run benchmark` заново обрабатывает три размеченных плана и завершается ошибкой, если доля совпавшей длины стен ухудшается более чем на 2 процентных пункта либо растёт число лишних или пропущенных окон/помещений. Те же проверки выполняются в `mise run test`. Базовые допуски — рабочая защита от регрессий, не доказательство качества на новых стилях планов. `3-floor-1.jpg` обработан без ошибки, но полного эталона для него нет; кладовки исключены из MVP.

## Первый реальный тест: plan.jpg

Исходный файл пользователя — [`plan.jpg`](plan.jpg), 1052 × 1162 px. Он сохранён отдельно от синтетического примера; viewer показывает отдельное приблизительное превью этого плана.

На изображении подписаны площади: гардеробная 4,3; две жилые комнаты 17,2 и 9,7; кухня 13,9; также 8,2, 5,3 и 2,73. Эти подписи пока прочитаны визуально, не OCR. Размерных линий с известной длиной нет: метрический масштаб не установлен. Высоты стен и проёмов на изображении также не определены.

### Запуск распознавания

```bash
mise exec -- uv run python -m recognizer.cli recognize plan.jpg \
  --output artifacts/my-plan-run
```

`--output` — **новый каталог**. Команда отказывается использовать существующий каталог и не меняет исходный файл. При ошибке записи новый незавершённый результат удаляется.

Внутри каталога создаются:

- `walls.json`: координаты осевых отрезков `[x, y]` в пикселях, толщина, идентификаторы и статус `candidate`;
- `overlay.png`: исходный план с полупрозрачным выделением толщины стен и подписями идентификаторов.

Результат текущего прогона: [наложение](artifacts/plan-walls/overlay.png), [JSON](artifacts/plan-walls/walls.json). Найдено **27 кандидатов**, JSON прошёл проверку схемы, координаты лежат в границах изображения. Масштаб неизвестен, `reviewRequired: true`. Это количество отрезков, а не подтверждённых физических стен.

Алгоритм использует порог Otsu, морфологическое удаление тонких штрихов, поиск длинных горизонтальных/вертикальных участков и группировку соседних строк/столбцов в осевые отрезки. Близкие коллинеарные отрезки объединяются. Параметры вычисляются из размера изображения; координат, специально прописанных для `plan.jpg`, в алгоритме нет. Используются тёмные штрихи на светлом фоне. На этом файле порог Otsu — 167, минимальная толщина — 5 px, минимальная длина — 43 px, объединяемый зазор — до 5 px.

Визуальная проверка наложения выявила:

- наружные стены и основные перегородки выделяются; большие дверные разрывы сохраняются;
- двойные контуры и ступенчатая толщина могут создавать несколько кандидатов одной стены, в частности `w009`/`w012`;
- нижний элемент у санузла (`w014`) может быть оборудованием, а не стеной;
- тонкие участки справа, границы окон и наружный контур правого выступа распознаны неполно;
- диагональные и тонкие стены, мебель с толстыми штрихами, слабый контраст и перекошенные сканы пока требуют отдельной обработки.

**Этот JSON нельзя загрузить в viewer как готовую квартиру.** Контракт кандидатов отдельно хранит `kind: "wall-candidates"`, источник изображения, параметры алгоритма и неопределённости. Комнаты, двери/окна, высоты и точный масштаб не выводятся из этих кандидатов автоматически. Команды `validate` и `calibrate` пока работают только с контрактом готовой квартиры. Результат кандидатов не является готовой квартирой; приблизительное сравнение полноценной обработки с эталонами приведено выше.

Добавлены 9 тестов распознавания: координаты/толщина и отсев тонкой мебели, дверной зазор, объединение малого разрыва, короткий толстый простенок, изменение разрешения, пустой/неверный ввод, схема/защита вывода, ошибка записи и ошибочный CLI-ввод. Исторический прогон после добавления распознавания: **4 TypeScript + 16 Python = 20 тестов**, все пройдены; `mise run validate` и `mise run build` также пройдены. Наложение реального результата просмотрено вручную.

Документация алгоритма: [морфология OpenCV](https://docs.opencv.org/4.x/d9/d61/tutorial_py_morphological_ops.html), [пороговая обработка OpenCV](https://docs.opencv.org/4.x/d7/d4d/tutorial_py_thresholding.html).

Для просмотра приняты **условные** 1 px = 1 см и высота стен 2,7 м; это не измерения. Стены взяты из нормализованных кандидатов, шесть контуров полов приблизительно обведены вручную. Под моделью показан исходный план, совмещённый с оценочным масштабом превью. Кнопка «Исходный план» переключает его и полы; при загрузке нового изображения подложка заменяется, а при импорте отдельного JSON отключается. При ручном редактировании координат подложка остаётся фиксированной. [Снимок превью](docs/verification/plan-preview.png); исходный синтетический пример остаётся доступен через открытие `viewer/public/examples/apartment.json`. Проверены Python-валидация, сборка и загрузка в Chromium.

## Кандидаты дверей и окон

```bash
mise exec -- uv run python -m recognizer.cli openings artifacts/plan-normalized/walls.json \
  --image plan.jpg --output artifacts/my-openings-run
```

Команда сохраняет в новом каталоге `openings.json` и `overlay.png`. Зелёный — кандидат двери, синий — окна, оранжевый — не определён. Алгоритм ищет разрывы между соосными отрезками, затем диагональные линии у края разрыва как возможное дверное полотно; окна предлагаются по близости к наружной оболочке или параллельным линиям внутри разрыва. Для широких оконных обозначений также анализируются две длинные параллельные линии у наружной границы с опорой на распознанные стены с обеих сторон. Это эвристики, не распознавание дуг; внешний контур невыпуклой квартиры и предметы мебели могут ошибочно классифицироваться. Отсутствующие или несовпадающие участки стен приводят к пропущенным проёмам.

В первом историческом прогоне найдено 8 кандидатов: [автоматическое наложение](artifacts/plan-openings/overlay.png), [результат](artifacts/plan-openings/openings.json). Все кандидаты требуют проверки. При визуальном просмотре `o006` отклонён как неподтверждённый, `o008` исправлен на кухонное окно; решения записаны в [review.json](artifacts/plan-openings/review.json). Остальные шесть отмечены как двери по условным обозначениям. Крупное окно справа сверху пока пропущено, поскольку его обрамление не образовало пару распознанных стен.

В `plan-preview.json` вручную перенесены 7 принятых проёмов: сегменты стен над дверями и под/над окном. Приняты условные высоты дверей 2,1 м, окна 1,4 м с подоконником 0,9 м и толщина добавленных сегментов 0,16 м. Изменение `review.json` пока не перестраивает 3D автоматически; для правки используйте JSON-редактор viewer. Ручная проверка проводилась только по этому изображению, точность не измерена.

## Нормализация кандидатов

```bash
mise exec -- uv run python -m recognizer.cli normalize artifacts/plan-walls/walls.json \
  --image plan.jpg --output artifacts/my-normalized-run
```

Команда создаёт новый каталог: `walls.json` содержит нормализованные отрезки, исходные `sourceIds` и `junctions` со списками примыкающих стен; `comparison.png` показывает исходные кандидаты слева и нормализованные справа, синим отмечены стыки. Существующие файлы не перезаписываются. Изображение проверяется по размерам, поэтому следует передавать исходный файл, а не другое изображение того же размера.

На `plan.jpg` получилось 26 кандидатов и 24 предполагаемых стыка: [сравнение](artifacts/plan-normalized/comparison.png), [JSON](artifacts/plan-normalized/walls.json). Близкие почти совпадающие параллельные отрезки объединяются; концы продлеваются только к ближайшим перпендикулярным пересечениям в пределах половины меньшей толщины. Дверные зазоры специально не закрываются. Вывод остаётся пиксельным и требует ручной проверки: часть дублей и ложных стыков сохраняется, граф представлен стенами и списками пересечений, а не готовыми полигонами комнат. Точность на реальном плане не измерена.

Проверено `mise run test`: 4 TypeScript и 18 Python тестов прошли. Дополнительные тесты проверяют объединение дублей, стык, сохранение дверного разрыва и отклонение диагональной стены. Сравнение реального плана просмотрено вручную.

## Система координат и масштаб

План использует `[x, y]`. Viewer преобразует их в Three.js `[x, высота, y]`, вертикальная ось — Y. `start/end` — осевые линии стен; их толщина центрирована относительно оси. Контуры помещений задаются отдельно и не выводятся автоматически из стен. Площадь в UI — сумма площадей контуров, без вычитания толщин стен.

`units: "m"` требует `scale.status: "known"` для измеренного масштаба либо `scale.status: "estimated"` для условного превью и непустой `scale.source`. Неизвестный масштаб хранится как `units: "px"`, `scale.status: "unknown"`. Такой документ можно валидировать и экспортировать, но построение метрической сцены запрещено. `uncertainties` содержит предупреждения об источнике данных и предполагаемых величинах.

Калибровка по известному отрезку (например, 250 px соответствуют 5 м):

```bash
mise exec -- uv run python -m recognizer.cli calibrate input-pixels.json \
  --reference-px 250 --meters 5 --output calibrated.json
```

В пиксельном документе **все линейные величины**, включая толщины и высоты, выражены в одной системе единиц. Калибровка умножает их на `meters/reference-px`, сохраняет исходный файл и отказывается перезаписывать существующий выходной файл. Она добавляет предупреждение: высоты/толщины и размеры проёмов требуют проверки. Калибровка 2D-масштаба сама по себе не определяет высоту помещения. Схема проверяет заявленный источник масштаба, но не доказывает его достоверность.

Проём содержит `wallId`, `offset` от начала оси стены, `width`, `bottom` от пола и `height`. Дверь начинается от пола. Вертикально разнесённые окна допускаются; перекрывающиеся прямоугольники запрещены.

## Повторное использование мебели

`models` сопоставляет `modelId` локальному URL вида `/models/chair.glb`. Файл разместите в `viewer/public/models/`. В `furniture` задайте `id`, `modelId`, `position: [x,y]`, `rotation` в радианах вокруг Y. Модели должны иметь метрический масштаб, точку начала на полу и ось Y вверх. Один GLB загружается один раз и клонируется для экземпляров. Ошибка загрузки показывается в интерфейсе и не препятствует построению квартиры. Анимированные/skinned-модели пока не поддерживаются. Качественная мебель и сами GLB-файлы в первый этап не входят.

## Управление

- Объём: левая кнопка — вращение, правая — сдвиг, колесо — приближение.
- План: камера сверху, вращение отключено, сдвиг и масштаб доступны.
- Прогулка: выберите режим и нажмите на сцену; WASD/стрелки — движение, мышь — обзор, Esc — освобождение курсора. Скорость 2.5 м/с, высота камеры 1.65 м. Это свободная камера **без столкновений**, можно проходить сквозь стены.
- Для корректировки измените JSON и нажмите «Перестроить квартиру». «Сохранить JSON» экспортирует текущий текст после валидации, включая документ с неизвестным масштабом.

## Границы прототипа

Распознавание стен ограничено прямыми горизонтальными/вертикальными отрезками; помещения и проёмы определяются эвристически и часто ошибочно. Нет очереди пакетной обработки, графического редактора, физики, крыши/потолка, створок дверей и окон. Комнаты — простые полигоны без отверстий; стены прямые, без автоматического объединения стыков. Перекрытия комнат и общая топология квартиры пока не проверяются. В углах стены могут перекрываться. Нет ограничений на размер пользовательского JSON, очень большие документы могут замедлить вкладку. Проект предназначен для локальных доверенных файлов.

Следующий этап: улучшить поиск оставшихся окон и помещений, расширить эталон на другие стили планов и проверить качество без изменения существующих трёх эталонов. Далее улучшать качество на новых стилях планов. Обработка MVP остаётся автоматической; масштаб без известного размера оценочный. Мебель до подтверждения универсального построения не детализируется.
